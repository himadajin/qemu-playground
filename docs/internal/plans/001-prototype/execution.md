# QEMU Playground Execution

## Purpose

任意の C・アセンブリコードを、自己ホスト環境を壊さずに複数ターゲットアーキテクチャ向けに隔離実行できる基盤を作る。
1 回の Run がコンパイルから QEMU 実行まで短命コンテナ内で完結し、結果(コンパイルログ、stdout、stderr、終了コード、C 入力時の生成アセンブリ)を安全に回収できる状態を目指す。

## Context

この文書は `design.md` の実行サンドボックス・ツールチェーンの決定領域を所有する companion である。
対象言語・ターゲット・コンパイラの選定(C とアセンブリ、RV64 + AArch64 の Linux user-mode、GCC)と API の形は `design.md` が、Docker Compose と配信の構成は `infrastructure.md` が扱う。

任意コードを実行するため、実行基盤は短命コンテナで隔離する。
Cloudflare Access により利用者は許可された少人数に限られるが、事故防止として時間制限、CPU/メモリ/PID 制限、ネットワークなしの実行を必須にする。
レート制限や強い公開サービス向け防衛策は初期設計に含めない。

runner は全ターゲットのツールチェーンを同居させた単一イメージとし、apt ベースで再現できる構成を優先して Ubuntu `24.04` を基準 OS とする。
runner イメージは linux/arm64 前提とする(自己ホストの arm64 ホストと Apple Silicon の開発機がともに arm64 のため)。
RV64 向けには apt から `gcc-riscv64-linux-gnu`、`binutils-riscv64-linux-gnu`、`libc6-dev-riscv64-cross` をインストールする。
AArch64 は arm64 ホストではネイティブアーキテクチャのため、apt の `gcc`、`binutils`、`libc6-dev` が提供する `aarch64-linux-gnu-*` の triplet 付きコマンドとヘッダ・ライブラリを使う。
libc ヘッダ(`libc6-dev` 系)は gcc パッケージの Recommends でしか入らないため、`--no-install-recommends` 構成では明示インストールが必須である。
QEMU は apt の `qemu-user` をインストールする。Ubuntu `24.04` の `qemu-user` は QEMU `8.2.2` 系で、`qemu-riscv64` と `qemu-aarch64` を提供する。
Linux user-mode に寄せることで、独自ツールチェーンビルドを初期設計から外す。

実行はホストとターゲットのアーキテクチャが一致する場合(arm64 ホスト上の AArch64 ターゲット)もネイティブ実行せず、全ターゲット一律で `qemu-<arch>` を明示起動する。
実行経路・リソース制限・シグナル回収の挙動を全ターゲットで同一に保ち、実行パスに条件分岐を作らないためである。

ターゲット定義(ツールチェーンコマンド、QEMU バイナリ名など)は `packages/shared` の静的な定義テーブルを単一の情報源とする。
ターゲットの追加は、runner イメージへの apt パッケージ追加とこの定義テーブルへの追記で完結する形を保つ。

## Direction

API サーバー本体はコンパイルや QEMU 実行を直接行わず、各 Run ごとに一時ディレクトリを用意し、短命 runner コンテナを起動してコンパイルと実行を完結させる。
runner コンテナ内で実行されるコマンド(コンパイラ、QEMU バイナリ)は、リクエストの `target` に応じてターゲット定義テーブルから引く。
Run ごとの作業ディレクトリは使い回さず、終了後に破棄する。

runner コンテナの起動は、API コンテナに Docker ソケット(`/var/run/docker.sock`)をマウントし、Docker API から制限付きの兄弟コンテナとして行う。
API コンテナが侵害された場合にホストの Docker を握られるトレードオフは、Cloudflare Access で利用者を許可した少人数に限定している前提で許容する。
ソケットは API コンテナ以外にマウントしない。

runner コンテナはネットワークなしで起動し、CPU、メモリ、PID、実行時間に制限をかける。
制限値は設定可能にしてよいが、初期値として少人数自己ホストで扱いやすい短時間実行を前提にする。
重い処理で落ちることは許容し、公開 SaaS 相当の防衛機能を作り込まない。

実行するプログラムの標準入力は常に空(即座に EOF を返す状態)で与える。
stdin を通じた入力供給は初期設計に含めない。

コンパイルログ、stdout、stderr の回収にはサイズ上限を設け、超過分は切り捨てる。
切り捨てが発生したことは結果から判別できるようにする。
上限値は設定可能にしてよいが、少人数自己ホストで扱いやすい控えめな初期値にする。

実行終了は、終了コードによる正常終了とシグナルによる異常終了を区別して回収する。
時間制限は Run 全体に対して適用してよいが、超過がコンパイル段階と実行段階のどちらで発生したかを判別できる形で回収する。

同時 Run は、Run ごとの独立コンテナと一時ディレクトリで分離する。
同時実行数には単純な上限を設け、上限を超えた Run は待ち行列に入れず即座にエラーとして返す。
キューやジョブ管理は作らない。
上限の初期値は Raspberry Pi 5 クラスのホストを想定した小さい値でよく、設定可能にしてよい。

コンパイルオプションはシェル文字列として直接実行せず、サーバー側で引数配列として扱う。
許可するオプション範囲は実装時に安全側で決めてよいが、任意のシェル実行やファイルシステム外参照を許す設計にはしない。

C 入力では、実行用バイナリとは別に `-S` 相当のコンパイルで生成アセンブリを取得する。
ユーザーが指定した最適化オプションなど、コード生成に影響するコンパイルオプションは、可能な範囲で実行用ビルドと生成アセンブリの両方に反映する。
実行用ビルドが成功していれば、生成アセンブリの取得に失敗しても Run 全体は失敗として扱わない。
その場合、生成アセンブリは空とし、失敗の内容はコンパイルログから読めるようにする。

アセンブリ入力では、ユーザーが選択したターゲットの Linux user-mode で実行できるアセンブリソースを書く前提にする。
コードとターゲットの整合はサーバーで検証せず、不整合はビルドエラーまたは実行時エラーとして返す。
C ランタイムを使う asm、または `_start` を定義する asm のどちらをサンプルとして採るかは実装時に単純な形を選ぶ。
複数ファイルリンクや独自リンカスクリプトは扱わない。

## Completion Conditions

- runner イメージが Ubuntu 24.04 と apt パッケージのみで、全ターゲットのツールチェーンを含む単一イメージとして linux/arm64 上で再現的にビルドできる。
- 各 Run は短命 runner コンテナ内で実行され、ネットワークなし、時間制限、CPU/メモリ/PID 制限、一時作業ディレクトリの破棄が適用される。
- RV64 と AArch64 のそれぞれで、C コードの Run からコンパイルログ、stdout、stderr、終了コード、生成アセンブリが回収される。
- RV64 と AArch64 のそれぞれで、アセンブリコードの Run からビルドログ、stdout、stderr、終了コードが回収される。
- 全ターゲットの実行が `qemu-<arch>` 経由で行われ、ホストネイティブなターゲットでも実行経路が変わらない。
- コンパイルエラー、実行時エラー、タイムアウト、通常終了が区別された結果として API サーバーが返せる状態になる。
- シグナルによる異常終了と非ゼロ終了コードの正常終了が区別して回収される。
- タイムアウトがコンパイル段階と実行段階のどちらで発生したかを判別できる。
- コンパイルログ、stdout、stderr にサイズ上限が適用され、切り捨ての発生が結果から判別できる。
- 複数ユーザーまたは複数タブからの同時 Run が、少人数自己ホスト用途として扱える範囲で衝突せず処理される。
- 同時実行数の上限を超えた Run は、キューに入らず即座にエラーとして返される。
